# 课题10实体链接智能体功能说明书

## 1. 文档说明

本文档说明当前版本实体链接智能体的功能范围、系统模块、数据流、接口能力、前端交互、工作流节点、异常处理和后续扩展方向。当前系统以“实体链接”为核心任务，支持将用户输入文本中的实体指称 mention 链接到指定知识库中的标准实体，并输出置信度、候选实体、证据、NIL 判断、歧义复核和共指结果。

当前版本同时支持两种使用方式：网页界面操作和 HTTP API 调用。网页界面面向演示与交互测试，HTTP API 面向系统集成与平台上传。

## 2. 系统目标

系统目标是构建一个可对话、可解释、可扩展的实体链接 Agent。它不仅能完成“文本 mention 到知识库实体”的自动链接，还需要具备以下能力：

- 支持用户通过自然语言对话提交文本和实体。
- 支持用户上传或导入本地知识库文件。
- 支持 CCKS2019 `kb_data`、通用 JSON、JSONL、PDF、TXT、Markdown 等输入格式。
- 支持对无候选实体输出 NIL，而不是强行链接。
- 支持对低置信、候选接近、语义风险较高的结果标记人工复核。
- 支持在复杂语境下进行共指处理，例如“他”“该公司”“这座城市”等回指。
- 支持大模型参与自然语言理解、别名扩展和候选复核。
- 支持在前端展示候选、置信度、证据、复核状态和大模型参与情况。
- 支持通过接口输出结构化 JSON，便于平台评测或后续系统调用。

## 3. 用户角色与典型场景

### 3.1 普通演示用户

用户通过浏览器访问系统，上传知识库，输入文本和实体，查看链接结果。重点关注界面是否直观、实体是否正确、错误结果是否能解释。

### 3.2 测试与评测用户

用户通过完整 LinkRequest JSON 调用接口，批量测试不同文本、不同知识库、不同阈值设置下的链接效果。重点关注接口稳定性、输出格式和可重复性。

### 3.3 开发与调试用户

用户关注 LangGraph 工作流节点、候选召回、评分公式、NIL 判定、复核分支、大模型参与情况和日志输出，用于继续改进算法效果。

## 4. 系统整体架构

当前系统采用前端展示层、API 服务层、智能体能力层、存储层分离的架构。

```text
用户 / 浏览器 / API 调用方
        |
        v
前端展示层 static/index.html
        |
        v
FastAPI API 服务层
        |
        v
Agent 对话服务 / 知识库导入服务 / 实体链接服务
        |
        v
LangGraph 实体链接工作流
        |
        v
候选召回、重排序、NIL、共指、大模型复核、证据生成
        |
        v
知识库 JSON 存储 / 名称索引 / 向量索引
```

系统的核心代码位于 `app` 目录，前端页面位于 `static/index.html`，文档位于 `docs` 和 `doc` 目录。

## 6. 前端功能说明

### 6.1 知识库管理页面

知识库管理页面用于导入和查看知识库。

主要功能如下：

- 从浏览器选择本地文件上传。
- 自动识别或手动选择文件来源类型。
- 支持导入后自动写入知识库存储。
- 支持预览导入结果中的实体数量和警告信息。
- 支持手动粘贴实体数组 JSON 或完整 KBPackage JSON。
- 支持查看当前系统已有知识库列表。
- 支持点击“使用”将某个知识库设置为当前实体链接知识库。

文件上传支持的来源类型包括：

- `auto`：自动识别。
- `ccks_kb_data`：CCKS2019 知识库数据格式。
- `kb_package`：系统完整知识库包格式。
- `entities`：实体数组 JSON 或 JSONL。
- `pdf`：PDF 文档。
- `text`：TXT 或 Markdown 文本。

PDF 和纯文本本身缺少固定结构，系统可以在配置大模型 API 后尝试抽取实体。如果无法转换，会返回结构化错误信息和 warnings。

### 6.2 实体链接页面

实体链接页面由左侧输入区和右侧结果展示区组成。

左侧输入区包含：

- Agent 对话框。
- 当前知识库选择框。
- 大模型选择框。
- 自然语言输入框。
- 对话区上传知识库入口。
- 高级 LinkRequest JSON 调试区。

右侧结果展示区包含：

- `mention` 总数按钮。
- `linked` 已链接实体按钮。
- `nil` NIL 实体按钮。
- `ambiguous` 歧义实体按钮。
- `review` 需要人工复核实体按钮。
- `大模型参与` 按钮。
- 搜索框，可按 mention、标准实体名、实体 ID、候选实体名搜索。
- 每个实体的链接状态、标准实体、置信度、证据、候选列表。
- 共指来源和共指链展示。

筛选按钮是真实交互按钮，点击后只显示对应类别实体。例如点击“大模型参与”后，仅显示 evidence 中包含大模型复核或大模型别名扩展信息的实体。

### 6.3 前端搜索功能

搜索框支持中文输入法，当前版本已经避免输入过程中重绘搜索框导致输入法候选栏消失的问题。搜索逻辑只刷新结果列表，不重建搜索输入框。

搜索范围包括：

- mention_id。
- surface_form。
- link_status。
- 标准实体 ID。
- 标准实体名。
- Top 候选实体 ID。
- Top 候选实体名。

## 7. Agent 对话功能说明

### 7.1 对话意图识别

Agent 对话层负责判断用户当前输入属于哪类请求。

支持的意图包括：

- `chat`：普通聊天或解释类问题。
- `help`：使用帮助。
- `link`：实体链接任务。
- `switch_kb`：切换知识库。
- `switch_model`：切换大模型。
- `upload_kb`：上传知识库引导。

只有当用户同时提供“原文文本”和“需要链接的实体 mention”时，系统才生成 LinkRequest 并提交实体链接 workflow。普通聊天、帮助问题、模型切换、知识库切换不会误提交 workflow。

### 7.2 本地快速解析

对于明确格式的输入，系统优先走本地解析，不调用远程大模型，从而降低延迟。

典型格式如下：

```text
文本：李导演的《断背山》真是令人动人
实体：李导演，断背山
```

或者：

```text
李导演的《断背山》真是令人动人，其中实体是李导演和断背山
```

本地解析会抽取 text.content 和 mentions，构造 LinkRequest，然后直接进入 LangGraph 实体链接流程。

### 7.3 大模型自然语言解析

如果用户输入不是明确的“文本/实体”格式，系统会根据当前大模型配置调用 OpenAI-compatible API，让大模型判断是否需要实体链接，以及是否能生成符合接口要求的 LinkRequest。

大模型解析主要用于：

- 判断用户到底是在聊天，还是在要求实体链接。
- 从自然语言中抽取文本和 mention。
- 对某些隐含指称生成 candidate_aliases，例如“李导演”可以提示“李安”。
- 根据用户指令切换知识库或模型。

### 7.4 默认回复与详细回复

当前版本默认回复保持简洁。用户提交文本和实体后，Agent 只返回本轮链接摘要，例如：

```text
实体链接已完成：共 126 个 mention，linked=124，ambiguous=1，nil=1，review=1。
```

只有当用户明确询问“详细、过程、流程、工作流、每个实体怎么处理、为什么、说明”等内容时，Agent 才会输出详细处理过程。

详细说明不是固定模板，而是根据本轮结果动态生成，包括：

- 是否使用本地解析或大模型解析。
- 是否触发候选级大模型复核。
- 是否存在共指处理。
- 是否存在人工复核。
- 每个实体的关键操作摘要。

当前系统使用 OpenAI-compatible Chat Completions 风格接口，支持多个 Provider。

支持的 API Key 环境变量包括：

- `LLM_API_KEY`
- `DEEPSEEK_API_KEY`
- `DEEPSEEK_APIKEY`
- `DEEPSEEK_KEY`
- `DEEPSEEK_API_TOKEN`
- `DASHSCOPE_API_KEY`
- `QWEN_API_KEY`
- `OPENAI_API_KEY`
- `SILICONFLOW_API_KEY`
- `MOONSHOT_API_KEY`
- `KIMI_API_KEY`
- `ZHIPU_API_KEY`
- `GLM_API_KEY`
- `ARK_API_KEY`
- `VOLCENGINE_API_KEY`

常用模型选择逻辑如下：

- `deepseek-*` 自动倾向 DeepSeek。

## 9. 知识库功能说明

### 9.1 知识库统一格式

系统内部使用统一实体结构：

```json
{
  "entity_id": "E001",
  "canonical_name": "国家电网有限公司",
  "entity_type": "ORG",
  "aliases": ["国家电网", "国网", "SGCC"],
  "former_names": [],
  "description": "中国大型电网企业，负责电力输送与销售。",
  "parent_ids": [],
  "keywords": ["电网", "输电", "电力"]
}
```

完整知识库包格式为：

```json
{
  "kb_id": "cn-enterprises-v1",
  "kb_version": "v1",
  "description": "中国企业实体库",
  "entities": []
}
```

### 9.2 知识库导入

系统支持以下导入方式：

- 手动 JSON 导入。
- 浏览器上传文件导入。
- 服务器本地路径导入。
- CCKS2019 `kb_data` 自动转换。
- PDF 或文本经大模型抽取后转换。

导入成功后，系统会生成或更新：

- 知识库元信息。
- 实体 JSON 文件。
- 名称索引。
- 向量索引状态。
- `entity_count` 统计。

`entity_count` 是根据导入后的实体列表长度生成的，不依赖用户手动填写。

### 9.3 知识库覆盖规则

如果导入的 `kb_id` 已存在，系统会覆盖旧知识库。覆盖后旧向量索引会失效，后续首次链接时会按新实体重新构建或加载索引。

## 10. LinkRequest 接口说明

实体链接核心请求格式如下：

```json
{
  "schema_version": "v1",
  "request_id": "req-demo",
  "text": {
    "content": "国家电网与华为在数字化转型项目中展开合作。",
    "language": "zh"
  },
  "mentions": [
    {
      "mention_id": "m1",
      "surface_form": "国家电网",
      "start_offset": 0,
      "end_offset": 4,
      "entity_type": null,
      "candidate_aliases": []
    }
  ],
  "knowledge_base": {
    "kb_id": "cn-enterprises-v1",
    "kb_version": "v1"
  },
  "options": {
    "top_k": 5,
    "nil_threshold": 0.6,
    "ambiguity_margin": 0.08,
    "auto_calibrate": true,
    "enable_llm_rerank": true,
    "enable_nil": true,
    "enable_coreference": true,
    "return_candidates": true,
    "return_evidence": true,
    "linker_version": "v1"
  }
}
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| `schema_version` | 接口版本 |
| `request_id` | 请求 ID，用于追踪 |
| `text.content` | 原文内容 |
| `mentions` | 待链接实体指称列表 |
| `surface_form` | 文本中的实体表面形式 |
| `start_offset` / `end_offset` | mention 在原文中的字符位置 |
| `entity_type` | 可选实体类型，未识别时可为空 |
| `candidate_aliases` | 可选别名提示，不是候选实体列表 |
| `knowledge_base` | 目标知识库 |
| `options` | 链接参数 |

`candidate_aliases` 为空是正常现象。它表示用户或大模型没有额外提供“可能标准名/别名提示”。真正的候选实体由 workflow 在知识库中召回，并在 LinkResponse 的 `candidates` 字段展示。

## 11. LinkResponse 输出说明

实体链接响应主要包括：

```json
{
  "schema_version": "v1",
  "request_id": "req-demo",
  "status": "success",
  "results": [],
  "coreference_chains": [],
  "summary": {
    "total_mentions": 2,
    "linked_count": 1,
    "nil_count": 1,
    "ambiguous_count": 0,
    "review_count": 0
  },
  "trace": {
    "linker_version": "v1",
    "kb_id": "cn-enterprises-v1",
    "kb_version": "v1",
    "options_used": {}
  }
}
```

单个结果包含：

- `mention_id`：mention ID。
- `surface_form`：实体表面形式。
- `link_status`：`linked`、`nil`、`ambiguous` 或 `error`。
- `entity`：链接到的标准实体。
- `confidence`：当前系统置信度分数。
- `candidates`：Top-K 候选实体。
- `evidence`：证据列表。
- `coreference`：共指来源。

## 12. LangGraph 工作流说明

当前实体链接 workflow 使用 LangGraph 编排，节点如下：

```text
START
  -> validate
  -> load_kb
  -> generate_candidates
  -> candidate_route
       -> empty -> nil_fallback -> END
       -> has_candidates -> rerank
  -> llm_rerank
  -> resolve
  -> coreference
  -> review_route
       -> auto_accept -> END
       -> needs_review -> human_review -> END
```

### 12.1 validate

输入校验节点。校验内容包括：

- `text.content` 不为空。
- `mentions` 不为空。
- 知识库存在。
- 知识库版本匹配。

如果校验失败，直接返回错误，不继续执行后续节点。

### 12.2 load_kb

加载知识库节点。主要工作包括：

- 加载实体列表。
- 构建名称索引 NameIndex。
- 加载或构建向量索引 VectorIndex。
- 生成知识库画像 KBProfile。
- 根据知识库特征自动校准参数。
- 生成当前知识库的评分权重。

知识库画像会统计别名密度、关键词密度、描述覆盖率、同名实体压力等信息，用于自适应调整阈值和权重。

### 12.3 generate_candidates

候选召回节点。对每个 mention 进行候选实体召回。

候选来源包括：

- 标准名精确命中。
- 别名精确命中。
- 曾用名精确命中。
- 向量语义召回。
- 字符相似度模糊召回。
- 描述性指称召回。
- 上下文别名扩展召回。

如果 mention 被识别为共指触发词，且存在可回指对象，则跳过候选召回，后续交给 coreference 节点处理。

### 12.4 candidate_route

候选路由节点。如果所有 mention 都没有候选，则进入 `nil_fallback` 分支，直接输出 NIL。否则继续进入 rerank。

### 12.5 nil_fallback

候选为空时的回退节点。该节点会将所有 mention 标记为 NIL，避免在无候选情况下误链接。

### 12.6 rerank

重排序节点。系统会结合候选原始分数、上下文关键词、实体类型、标准名/别名命中、先验信息、别名扩展等特征重新计算候选分数。

排序时不仅看分数，还会优先保护可信精确命中：

```text
canonical_match > alias_match > former_name_match > similarity_match
```

这样可以减少“向量分数较高但语义错误”的候选挤掉精确别名候选的问题。

### 12.7 llm_rerank

大模型候选复核节点。当候选分数接近、存在歧义或风险较高时，系统会把候选列表、上下文、实体描述和关键词发送给大模型，让大模型在候选列表中选择最合理实体。

该节点具备以下约束：

- 只允许大模型从系统已召回候选中选择。
- 不允许大模型凭空创造知识库外实体。
- 只有置信度达到内部要求才接受复核结果。
- 接受后会给候选加 `llm_rerank_support` 证据。
- 前端会将这类实体标记为“大模型参与”。

如果没有 API Key、模型不可用、候选不需要复核或请求失败，该节点不会中断主流程。

### 12.8 resolve

决策解析节点。根据 Top 候选分数、NIL 阈值、歧义间隔和候选证据决定最终状态：

- `linked`：成功链接。
- `ambiguous`：候选接近，需要复核。
- `nil`：无可靠库内实体。

### 12.9 coreference

共指消解节点。负责处理“他”“该公司”“这座城市”“那座古城”等回指或后指表达。

当前支持：

- 前文实体回指。
- 后文实体后指。
- 同位语结构。
- 描述性称谓。
- 指代词触发词。

共指成功后，结果中会显示：

- `coreference.resolved_from`
- 共指链 `coreference_chains`
- evidence 中的 `coreference`

### 12.10 review_route 与 human_review

复核路由节点会检查结果是否需要人工复核。

进入复核的典型情况包括：

- `link_status` 为 `ambiguous`。
- NIL 但仍存在候选。
- NIL 且来自共指。
- 已链接但置信度低于阈值。

进入 human_review 后，系统不会替用户改结果，而是追加 evidence：

```text
human_review_required: low_confidence_or_ambiguous
```

前端会显示 `需复核` 标记，用户可点击 review 按钮集中查看。

## 13. 候选召回与消歧能力

### 13.1 精确召回

系统会对 mention 和知识库实体的以下字段建立索引：

- `canonical_name`
- `aliases`
- `former_names`

精确召回优先级最高，能够处理简称、英文缩写和曾用名。

例如：

- `国网` -> `国家电网有限公司`
- `SGCC` -> `国家电网有限公司`
- `神华集团` -> `国家能源投资集团有限责任公司`

### 13.2 向量召回

如果本地嵌入模型和 FAISS 索引可用，系统会使用向量语义检索召回候选。向量召回适合处理描述性表达或字面不完全一致的 mention。

如果模型路径不存在，系统会降级为规则召回，不影响主流程运行。

### 13.3 模糊召回

模糊召回用于处理轻微错别字、简称和相似字符串。但当前版本已经防止模糊召回“伪装成 alias_match”。也就是说，只有真正等于标准名、别名或曾用名的字符串才会标记为可信精确命中。

### 13.4 描述性召回

系统可以根据 mention 周边上下文和实体描述/关键词匹配，处理部分描述性指称。例如“这座湖”“那家互联网公司”等需要结合上下文判断的表达。

## 14. 置信度计算说明

当前置信度不是单一大模型概率，而是系统综合计算得到的链接分数。它表示“当前候选在本知识库和当前上下文下被接受的可信程度”。

主要影响因素包括：

- mention 与标准名/别名/曾用名的匹配程度。
- 向量语义相似度。
- 上下文关键词命中。
- 实体描述与上下文重叠。
- mention 类型与候选实体类型是否一致。
- 标准名命中加权。
- 别名先验加权。
- 上下文别名扩展加权。
- 大模型候选复核加权。
- 自适应知识库画像参数。

因此，置信度更接近“可解释的排序分数”，不是严格统计意义上的真实概率。

## 15. NIL 与歧义处理说明

### 15.1 NIL

当系统判断 mention 没有可靠库内实体时，输出 NIL。

常见 NIL 场景：

- 知识库中没有该实体。
- 候选为空。
- 候选只来自低质量相似度召回。
- Top 候选低于 `nil_threshold`。

### 15.2 Ambiguous

当 Top1 和 Top2 候选分数过近时，系统输出 ambiguous 或进入人工复核标记。

歧义处理不是系统失败，而是为了避免强行链接错误实体。例如知识库中存在多个“杭州”“西湖”“断背山”等同名实体时，系统会更谨慎。

### 15.3 Review

review 表示系统认为结果需要人工确认。前端提供 review 筛选按钮，便于集中查看。

## 16. 大模型参与的边界

当前大模型不是替代整个实体链接流程，而是作为 Agent 中的一个能力模块。

大模型主要参与：

- 自然语言意图判断。
- 非结构化输入转 LinkRequest。
- 复杂 mention 的 candidate_aliases 提示。
- 候选接近时的 llm_rerank 复核。
- PDF 或文本知识库抽取。

大模型不负责：

- 直接修改知识库。
- 直接输出最终实体 ID。
- 在没有候选时凭空创造库内实体。
- 绕过 NIL 和人工复核机制。

这样设计可以兼顾可解释性、稳定性和可控性。

## 20. 当前版本特点

当前版本相较于早期版本，主要增强如下：

- 使用 LangChain + LangGraph 编排实体链接 workflow。
- 引入 candidate_route，候选为空时走 NIL 分支。
- 引入 review_route，低置信或歧义时走人工复核分支。
- 引入 llm_rerank 节点，让大模型参与候选级复核。
- 支持多 provider API Key 自动识别。
- 支持前端对“大模型参与”的实体进行筛选。
- 支持前端 linked、ambiguous、NIL、review 按钮筛选。
- 支持前端实体搜索。
- 支持中文输入法搜索修复。
- 默认 Agent 回复简洁，用户明确要求时才输出详细过程。
- 精确别名命中不会被向量召回分数漂移覆盖。
- 模糊召回不会伪装为 alias_match。
- 支持知识库画像和自适应阈值/权重。

## 21. 当前限制

当前系统仍有以下限制：

- 置信度是可解释综合分数，不是经过大规模训练校准的概率。
- 大模型复核依赖外部 API，网络延迟和额度会影响效果。
- PDF 和纯文本知识库抽取质量依赖文档结构和大模型能力。
- 多知识库泛化依赖实体字段质量，如果知识库缺少别名、描述、关键词，消歧效果会下降。
- 共指能力覆盖了常见规则场景，但不能保证处理所有复杂语言现象。
- 前端目前是单文件页面，适合演示，若做正式产品可拆分为工程化前端。
